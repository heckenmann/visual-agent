# Dependency and distribution license audit

Audit date: 2026-09-28. Scope: Issue [#47](https://github.com/heckenmann/visual-agent/issues/47), repository `master` at the start of the audit, macOS arm64 dependency resolution. This is an engineering compliance inventory, not a legal opinion.

## Method and reproducibility

Run `./gradlew generateLicenseReport --no-daemon --no-parallel --no-configuration-cache`. The maintained [Gradle License Report plugin](https://github.com/jk1/Gradle-License-Report) 3.1.4 scans `compileClasspath`, `runtimeClasspath`, and `testRuntimeClasspath` of every project plus build-script projects; it emits `build/reports/dependency-license/licenses.csv` and `index.html`. `--no-parallel` follows the plugin's [Gradle 9 limitation](https://github.com/jk1/Gradle-License-Report/blob/master/README.md#gradle-9). The checked-in [CSV snapshot](dependency-licenses-2026-09-28.csv) contains 477 resolved artifact coordinates and POM-derived license declarations. It is evidence, not a license grant or a substitute for artifact-level inspection. It merges scopes and can list multiple versions of the same artifact because modules resolve independently. The snapshot is **macOS arm64-specific**; rerun on Windows and Linux before release.

Run `./gradlew -I scripts/license-settings.init.gradle.kts generateBuildPluginInventory --no-daemon --no-parallel --no-configuration-cache` for the separate plugin-DSL classpath inventories. The [project-build CSV snapshot](build-plugin-dependencies-2026-09-28.csv) contains 63 resolved coordinates across the root and 12 module builds, with the projects that load each one. Of these, 53 coordinates do not occur in the application/test license CSV. The [settings-build CSV snapshot](settings-plugin-dependencies-2026-09-28.csv) contains the Foojay plugin marker and implementation, which load before project configuration. Both reports read Gradle's selected component identities, not rendered dependency-tree text. None of the CSVs contains license texts or embedded native-component inventories.

The application report covers all 64 used catalog library aliases, including the macOS Netty classifier, and resolved transitive artifacts. The separate plugin report covers project build-script classpaths, but neither report resolves JDK modules, downloaded AppImage tools, native code or fonts embedded inside JARs, or local assets. Those are inventoried below. BOMs are version constraints, not shipped code. `compileOnly` is not a runtime dependency. Build/test-only artifacts are not automatically part of the application distribution.

Run `./gradlew generateDependencyScopeInventory --no-daemon --no-parallel --no-configuration-cache` for `build/reports/dependency-license/dependency-scopes.csv`. It lists every resolved Maven coordinate with its project and `compileClasspath`, `runtimeClasspath`, or `testRuntimeClasspath` membership. These are Gradle classpaths, not mutually exclusive license categories: `compileOnly` contributes to compilation, and an artifact on `testRuntimeClasspath` may also be a runtime dependency. The local report has 3,353 project/configuration rows and 480 distinct coordinates. Three test-only coordinates are present here but omitted by the license-report plugin: `org.jetbrains.kotlin:kotlin-test-junit5:2.4.20`, `org.jetbrains.kotlin:kotlin-test-junit:2.4.20`, and `org.junit.platform:junit-platform-launcher:6.1.3`. The two Kotlin artifacts are covered by [Kotlin's Apache-2.0 license](https://github.com/JetBrains/kotlin/blob/master/license/LICENSE.txt); the JUnit launcher is covered by [JUnit 5's EPL-2.0 license](https://github.com/junit-team/junit5/blob/main/LICENSE.md). None of the three is in the inspected desktop package. Do not treat the 477-row POM CSV alone as a complete resolved-component inventory.

The POM scanner reports one declared license per row, sometimes omitting alternative licenses: [Logback](https://logback.qos.ch/license.html) is EPL-2.0 **or** LGPL-2.1, [JNA](https://github.com/java-native-access/jna/blob/master/README.md#license) is Apache-2.0 **or** LGPL-2.1+, and [H2](https://h2database.com/html/license.html) is MPL-2.0 **or** EPL-1.0. The human assessment below uses these upstream statements. No global allow-list is applied because a license string alone cannot prove artifact contents or compliance.

All 477 CSV rows contain a POM license declaration, but 27 rows lack either a project URL (26) or a license URL (one); this is a metadata limitation, not evidence that the license is absent. Among the packaged artifacts with incomplete metadata, [DBus-Java](https://github.com/hypfvieh/dbus-java/blob/master/LICENSE) states MIT, while [OpenAI Java](https://github.com/openai/openai-java/blob/main/LICENSE) and [VicTools JSON Schema Generator](https://github.com/victools/jsonschema-generator/blob/main/LICENSE) state Apache-2.0. The DBus-Java transport JAR and VicTools Swagger 2 module are included in the inspected macOS package. These upstream files support the human assessment, but the remaining incomplete URLs should be reviewed alongside platform-specific release graphs rather than interpreted as complete automatically.

Run `./gradlew :desktop:generateDistributionArtifactInventory --no-daemon --no-parallel --no-configuration-cache` to build the app image and write `modules/desktop/build/reports/dependency-license/packaged-artifacts.csv`. This maps packaged JAR filenames to resolved `runtimeClasspath` artifacts using Compose's MD5-based filename suffix (each digest byte is written without zero-padding). The MD5 suffix is a packaging identifier, **not** an integrity or license proof. The report records both the resolved source JAR's and packaged JAR's SHA-256; packaging can alter bytes. `UNMATCHED` and `AMBIGUOUS` rows require manual review rather than a guessed coordinate. On the inspected macOS build, 271 of 274 JARs map to a resolved artifact; the three exceptions are the local `:desktop` JAR, the jlink runtime's `jrt-fs.jar`, and a packaged Skiko runtime JAR. `org.jetbrains.skiko:skiko-awt-runtime-macos-arm64:0.150.1` is the matching resolved coordinate by name, but the packaged JAR and its embedded native binaries are not byte-identical to that cached artifact. Its exact provenance or packaging transformation needs release verification; the generated report does not claim an exact match.

After building an app image, run `bash scripts/generate-package-inventory.sh <app-image-directory> build/reports/dependency-license`. It writes package file paths, native/font/AFM entries embedded inside JARs, and in-JAR LICENSE/NOTICE/COPYING paths. The [license-inventory workflow](../.github/workflows/license-inventory.yml) runs the license, plugin, scope, and packaged-artifact reports plus this package scan on each release-runner platform and uploads them for comparison. Paths inside JARs are an inventory, not a complete license classification.

### macOS package inspection

`./gradlew :desktop:createDistributable --no-daemon --no-parallel` produced a macOS arm64 `.app` containing 273 application JARs and a separate `libskiko-macos-arm64.dylib`. The included jlink runtime identifies itself as Temurin 25.0.3 and retains 35 files under `Contents/runtime/Contents/Home/legal/`; `keytool` is present. The nested-asset scan found 60 native/font/AFM entries across 13 JARs, including multi-platform binaries in gRPC, JNA, Netty and Graal. Gradle resolves `org.jetbrains.skiko:skiko-awt-runtime-macos-arm64:0.150.1` on the desktop runtime classpath. Its cached JAR contains both arm64 and x64 libraries, whereas the packaged JAR contains only an x64 library and the app has a separate arm64 library. The packaged x64 library is 22,172,720 bytes versus 22,190,816 bytes in the cached JAR; its exact packaging transformation and notices require verification. This is a package-content observation, not evidence that the wrong library loads. Among the 273 JARs, 133 contain a file whose name matches LICENSE, NOTICE, or COPYING and 140 do not. The only TTF/OTF/WOFF file found within those JARs is PDFBox's Liberation Sans font. PDFBox includes `META-INF/LICENSE` and `META-INF/NOTICE`; JNA includes `META-INF/LICENSE`; the inspected H2, Logback Core, and Skiko runtime JARs do not have such a named file. Absence of an in-JAR license does not by itself prove noncompliance, but this package has no separate third-party license/NOTICE bundle for the application JARs or the Skiko library. This inspection is **one local macOS build**, not evidence for CI's exact vendor or the Windows/Linux packages.

## Distribution decision and checklist

**Source:** The project may remain MIT-licensed. Third-party libraries keep their own licenses; the root `LICENSE` applies only to Visual Agent's own material. Source publication is acceptable provided third-party files are not relabeled as MIT and asset ownership is confirmed.

**Current binary release posture:** Do **not** describe the DMG/MSI/DEB/RPM/AppImage/JAR matrix as fully cleared. No top-level `NOTICE` or consolidated third-party license bundle currently exists, and release packaging does not explicitly stage such a bundle. AppImage's statically linked libfuse is the most consequential unresolved obligation. `gh release list` returned no published or draft GitHub releases on 2026-09-28, so there is no existing GitHub release asset to supplement; the release gate must be ready before the first publication. The [license-inventory workflow](../.github/workflows/license-inventory.yml) is prepared to publish dependency and app-image file manifests from the four release runner platforms, but its results must be inspected after it runs on a pushed branch; the local macOS run does not substitute for them.

- [ ] Regenerate the license inventory on macOS arm64/x64, Windows x64, and Linux x64 using the exact release dependency graph; diff platform-specific classifiers and package contents against the report.
- [ ] Inspect every packaged JAR and native payload for LICENSE/NOTICE/COPYING files, especially Skiko/Skia, JNA, Netty, GraalJS, PDFBox, Tika, and the trimmed JDK. Preserve required notices, copyright and modification statements.
- [ ] Create a versioned third-party license bundle with full applicable license texts, per-component attributions and upstream notices. Include the project's MIT `LICENSE` separately.
- [ ] Include the bundle in each native installer/AppImage and with each executable JAR release; make it reachable from README and the app's About/help surface.
- [ ] For H2, ship the license and liability disclaimer requested by its [license FAQ](https://h2database.com/html/license.html). For Logback select and state the EPL-2.0 option; for JNA select and state Apache-2.0, subject to its own bundled native components.
- [ ] Verify the AppImage Type 2 runtime's statically linked libfuse LGPL obligations with the exact binary/source build and supply corresponding source or another compliant mechanism where required.
- [ ] Check the exact JDK vendor and license files included by jpackage on each CI runner; do not infer a Linux/macOS/Windows package from a macOS-only scan.
- [ ] Obtain and record project-owner confirmation of icon provenance and rights; record generation/conversion commands for raster/native variants.
- [ ] Add a release gate that fails when an artifact lacks its expected license bundle or when the resolved dependency report changes without review.

The root `LICENSE` should remain MIT, not be replaced with a combined license. The README now links this audit; it should also link the eventual distributable notice bundle. A new `NOTICE` or `THIRD_PARTY_LICENSES` file, an About/help link, and release-workflow staging are required **before asserting binary compliance**. Follow-up issues track [binary notice delivery and AppImage obligations](https://github.com/heckenmann/visual-agent/issues/410), [icon provenance](https://github.com/heckenmann/visual-agent/issues/411), and [build/plugin/platform inventory gaps](https://github.com/heckenmann/visual-agent/issues/412).
