## Method and reproducibility

Run `./gradlew generateLicenseReport --no-daemon --no-parallel --no-configuration-cache`. The maintained [Gradle License Report plugin](https://github.com/jk1/Gradle-License-Report) 3.1.5 scans `compileClasspath`, `runtimeClasspath`, and `testRuntimeClasspath` of every project plus build-script projects; it emits `build/reports/dependency-license/licenses.csv` and `index.html`. `--no-parallel` follows the plugin's [Gradle 9 limitation](https://github.com/jk1/Gradle-License-Report/blob/master/README.md#gradle-9). The checked-in [CSV snapshot](dependency-licenses-2026-10-01.csv) contains 477 resolved artifact coordinates and POM-derived license declarations, regenerated against the current PR base dependency versions. It is evidence, not a license grant or a substitute for artifact-level inspection. It merges scopes and can list multiple versions of the same artifact because modules resolve independently. The snapshot is **macOS arm64-specific**; rerun on Windows and Linux before release.

## Tooling assessment (2026-11-07)

The current [OSS Review Toolkit (ORT)](https://oss-review-toolkit.org/ort/) release is 98.0.0 (published 2026-11-05). Its official [Analyzer documentation](https://oss-review-toolkit.org/ort/docs/tools/analyzer) lists Gradle support and produces a dependency graph with package metadata; its [toolchain](https://oss-review-toolkit.org/ort/docs/category/tools) also provides source downloading, scanner integration, policy evaluation, and SPDX/CycloneDX plus customizable reports. This is broader than the existing Gradle License Report plugin, which is already configured here for resolved Gradle classpaths and primarily supplies dependency license metadata. Its [official documentation](https://github.com/jk1/Gradle-License-Report#configuration) describes POM metadata, license overrides, and report renderers, but not a license-text downloader; it therefore does not replace retrieval and verification of original license/NOTICE bytes.

ORT could replace or supplement the POM-metadata inventory and could help collect and scan source for supported Gradle dependencies. It would not by itself replace this project's checks against the actual generated JARs, app images, platform-specific native package payloads, embedded JAR notices, or transformations performed during packaging. Those require evidence from the exact built artifacts. ORT also cannot decide whether a particular license condition is satisfied or recover unavailable build inputs. The project already has version-specific package inventories and corresponding-source collection for areas where the general dependency graph is insufficient.

**Decision for Issue #410:** Do not add ORT to the release-closure path. The incremental scanner/policy/reporting capability does not remove the remaining package-specific work, while introducing a second analysis configuration and runtime to maintain. Keep Gradle License Report as the Maven/Gradle metadata inventory and retain only the custom collection and verification that bind materials to the actual packaged artifacts. Reconsider ORT separately if the project adopts a broader recurring SBOM, source-scanning, or policy-evaluation requirement. This is a tooling-scope decision, not a compliance finding.

Run `./gradlew -I scripts/license-settings.init.gradle.kts generateBuildPluginInventory --no-daemon --no-parallel --no-configuration-cache` for the separate plugin-DSL classpath inventories. The [project-build CSV snapshot](build-plugin-dependencies-2026-09-28.csv) contains 63 resolved coordinates across the root and 12 module builds, with the projects that load each one. Of these, 53 coordinates do not occur in the application/test license CSV. The [settings-build CSV snapshot](settings-plugin-dependencies-2026-09-28.csv) contains the Foojay plugin marker and implementation, which load before project configuration. Both reports read Gradle's selected component identities, not rendered dependency-tree text. None of the CSVs contains license texts or embedded native-component inventories.

The application report covers all 64 used catalog library aliases, including the macOS Netty classifier, and resolved transitive artifacts. The separate plugin report covers project build-script classpaths, but neither report resolves JDK modules, downloaded AppImage tools, native code or fonts embedded inside JARs, or local assets. Those are inventoried below. BOMs are version constraints, not shipped code. `compileOnly` is not a runtime dependency. Build/test-only artifacts are not automatically part of the application distribution.

Run `./gradlew generateDependencyScopeInventory --no-daemon --no-parallel --no-configuration-cache` for `build/reports/dependency-license/dependency-scopes.csv`. It lists every resolved Maven coordinate with its project and `compileClasspath`, `runtimeClasspath`, or `testRuntimeClasspath` membership. These are Gradle classpaths, not mutually exclusive license categories: `compileOnly` contributes to compilation, and an artifact on `testRuntimeClasspath` may also be a runtime dependency. The current report has 3,353 project/configuration rows and 480 distinct coordinates. Three test-only coordinates are present here but omitted by the license-report plugin: `org.jetbrains.kotlin:kotlin-test-junit5:2.4.20`, `org.jetbrains.kotlin:kotlin-test-junit:2.4.20`, and `org.junit.platform:junit-platform-launcher:6.1.3`. The two Kotlin artifacts are covered by [Kotlin's Apache-2.0 license](https://github.com/JetBrains/kotlin/blob/master/license/LICENSE.txt); the JUnit launcher is covered by [JUnit 5's EPL-2.0 license](https://github.com/junit-team/junit5/blob/main/LICENSE.md). None of the three is in the inspected desktop package. Do not treat the 477-row POM CSV alone as a complete resolved-component inventory.

The POM scanner reports one declared license per row, sometimes omitting alternative licenses: [Logback](https://logback.qos.ch/license.html) is EPL-2.0 **or** LGPL-2.1, [JNA](https://github.com/java-native-access/jna/blob/master/README.md#license) is Apache-2.0 **or** LGPL-2.1+, and [H2](https://h2database.com/html/license.html) is MPL-2.0 **or** EPL-1.0. The human assessment below uses these upstream statements. No global allow-list is applied because a license string alone cannot prove artifact contents or compliance.

All 477 CSV rows contain a POM license declaration, but 26 rows lack either a project URL (25) or a license URL (one); this is a metadata limitation, not evidence that the license is absent. Among the packaged artifacts with incomplete metadata, [DBus-Java](https://github.com/hypfvieh/dbus-java/blob/master/LICENSE) states MIT, while [OpenAI Java](https://github.com/openai/openai-java/blob/main/LICENSE) and [VicTools JSON Schema Generator](https://github.com/victools/jsonschema-generator/blob/main/LICENSE) state Apache-2.0. The DBus-Java transport JAR and VicTools Swagger 2 module are included in the inspected macOS package. These upstream files support the human assessment, but the remaining incomplete URLs should be reviewed alongside platform-specific release graphs rather than interpreted as complete automatically.

Run `./gradlew :desktop:generateDistributionArtifactInventory --no-daemon --no-parallel --no-configuration-cache` to build the app image and write `modules/desktop/build/reports/dependency-license/packaged-artifacts.csv`. This maps packaged JAR filenames to resolved `runtimeClasspath` artifacts using Compose's MD5-based filename suffix (each digest byte is written without zero-padding). The MD5 suffix is a packaging identifier, **not** an integrity or license proof. The report records both the resolved source JAR's and packaged JAR's SHA-256; packaging can alter bytes. `UNMATCHED` and `AMBIGUOUS` rows require manual review rather than a guessed coordinate. An older macOS snapshot mapped 271 of 274 JARs and recorded a Skiko 0.150.1 filename/coordinate mismatch plus the local project and JDK JARs. That snapshot predates the current Skiko 0.150.2 dependency and is historical only; see the dated current-worktree inventory note below. It must not be used to infer the provenance of a new release candidate.

After building an app image, run `bash scripts/generate-package-inventory.sh <app-image-directory> build/reports/dependency-license`. It writes package file paths, native/font/AFM entries embedded inside JARs, and matching in-JAR `LICENSE`, `LICENCE`, `NOTICE`, `COPYING`, `COPYRIGHT`, `DISCLAIMER`, and `AUTHORS` files. It excludes archive directory entries and class files under paths such as `META-INF/license/`. The [license-inventory workflow](../.github/workflows/license-inventory.yml) runs the license, plugin, scope, and packaged-artifact reports plus this package scan on each release-runner platform and uploads them for comparison. Paths inside JARs are an inventory, not a complete license classification.

The earlier macOS snapshot below is historical and must not be used as current release evidence. A local ARM64 app image built from the current worktree on 2026-11-08 contained 278 JARs: 262 external runtime artifacts, 15 project-module JARs, and the bundled JDK `jrt-fs.jar`. All 278 rows mapped uniquely; there were no `UNMATCHED` or `AMBIGUOUS` entries. This worktree is uncommitted and is not a release candidate. Unique artifact mapping also does not establish that the complete applicable license, notice, or source materials are present.

The local ARM64 notice manifest was regenerated from that app image after the current legal-material changes. It contains 263 third-party/runtime entries: 262 have license declarations in the generated Gradle report, while the bundled `jrt-fs.jar` is linked to the separately retained JDK runtime legal files. The manifest retains 136 detected in-JAR notices and records no notice for 127 entries; 21 entries have exact-source-hash supplemental material, and the JDK legal directory contains 242 files. Every entry remains `unreviewed` and `redistributionApproved` is false. These single-platform counts help scope review; they are not a determination that every no-notice item needs an additional text or that the reviewed materials are complete.

The successful [license inventory run `42386575613`](https://github.com/heckenmann/visual-agent/actions/runs/42386575613) independently generated notice manifests for Windows x64, Linux x64, macOS x64, and macOS ARM64 from the then-current CI dependency graph. The manifests map 264 packaged JARs on Windows, Linux, and macOS ARM64, and 262 on macOS x64. Each marks every component `unreviewed`; 136 rows per platform have a detected in-JAR notice, while 128 have none (126 on macOS x64). These counts are triage evidence, not a count of missing legal obligations: the no-notice rows still require license-text/source mapping, and detected text still requires review. The inventories are not final release artifacts and do not establish recipient-facing completeness.

`./gradlew :desktop:createDistributable --no-daemon --no-parallel` produced a macOS arm64 `.app` containing 273 application JARs and a separate `libskiko-macos-arm64.dylib`.
